# ADR-001：模型推理演进与 Embedding 选型

- **状态**：已采纳
- **背景**：项目需满足基于开源 LLM、支持 `>32k tokens` 长上下文、可迭代微调，且 MVP 阶段需优先低成本快速跑通。

## 1. 大语言模型接入取舍
- **备选方案**：
  - A. 起步直接部署本地开源模型并微调（前期环境与算力阻塞风险高）。
  - B. MVP 先接 **DeepSeek 云端 API**（OpenAI 兼容协议，支持 `>32k` 上下文），后期无缝切换为本地开源模型（如 Qwen2.5）+ LoRA/SFT 微调。
- **决策**：采用 **方案 B**。
- **理由**：快速验证 RAG 链路与基线指标，且统一封装 OpenAI 兼容层后，后期切换本地 vLLM/Ollama 推理服务只需改配置，无架构返工。

## 2. Embedding 方案取舍
- **备选方案**：
  - A. 全程使用阿里云百炼免费额度 Embedding API。
  - B. 默认采用本地轻量中文模型（`BAAI/bge-small-zh-v1.5`），同时在接口层兼容阿里云百炼 Embedding API 供后期对比。
- **决策**：采用 **方案 B**。
- **理由**：5,000+ 条 CMedQA 语料单次建库即消耗约 75 万–150 万 tokens，叠加小组多人开发与反复调整切块重建索引，云端免费额度极易耗尽并阻塞协作；本地 `bge-small-zh-v1.5` 体积小（~95MB）、免费离线可复现，后期可在 V2 阶段按需接入云端模型做消融对比。
